# ADR-002: 書架の一覧の状態は URL のクエリを正とする

## ステータス

承認済み（Accepted、2026-09-14 決定）

## タグ

`書架` `一覧` `URL` `履歴` `localStorage`

## コンテキスト

**きっかけ**：2026-09-14、書架の使い勝手について3つの指摘を受けた。

1. リロードすると1ページ目に戻ってしまう
2. ブラウザの戻るボタンで直前の状態に戻れず、書架そのものから出てしまう
3. 並べ替えと表示形式を毎回選び直すことになる

**観察した事実**：

- 一覧の絞り込み・ページ送り・表示形式は、すべて `app/components/BookmarkArchive.tsx` の React state だけで持っていた。URL は `/` のまま変わらないため、**リロードすると初期値に戻る**
- ブックマークは全件をサーバーで取得して渡しており（`app/app/page.tsx`）、絞り込みもページ送りもクライアント側の処理。**URL が変わってもサーバーから取り直す必要はない**
- 1 の指摘を受けて一度 `history.replaceState` で URL に写す実装を入れたが、**履歴が積まれないため 2 は解決しなかった**（戻ると書架に入る前の画面へ出てしまう）
- テーマ（淡／濃）は `localStorage` に記憶する実装が既にある（`app/utils/theme.ts`、キーは `tube-bookmark:theme`）

**既存ドキュメントで判断できなかった理由**：[ユビキタス言語](../ubiquitous-language.md) は「絞り込み」「表示順」などの語を定めるが、その状態をどこに持つかは扱わない。[ADR-001](adr-001-capture-via-app-api.md) は拡張からの登録経路の判断で、一覧の話を含まない。

## Intent（意図）

1. **最優先：見ている状態を失わないこと。** リロード、戻る、ページの共有のいずれでも、同じ絞り込み・同じ並び・同じページに戻る
2. **次点：操作に対する反応を遅くしないこと。** 並べ替えやページ送りのたびにサーバーへ取りに行かない
3. **次点：毎回選び直す手間を無くすこと。** 並べ替えと表示形式は前回の選び方から始める
4. **将来：状態が増えても同じ置き場で扱えること。** 編集中のような新しい状態を足すときに、別の仕組みを持ち込まない

## 選択肢

### 案A: React state だけで持つ（変更前の実装）

**メリット:**

- 実装が単純。URL を気にしなくてよい

**デメリット:**

- リロードで初期値に戻る（Intent 1 を満たさない）
- 戻るボタンが書架の外へ出る
- 状態を人に渡せない（URL を送っても同じ画面にならない）

### 案B: URL のクエリを正とし、history API で書く（推奨）

**メリット:**

- リロード・戻る・共有のすべてで同じ画面になる
- ページ遷移を伴わないので、サーバーから取り直さない
- 状態が増えてもクエリを1つ足すだけで済む

**デメリット:**

- URL が長くなる
- 「どの操作で履歴を積むか」を操作ごとに決める必要がある

### 案C: すべて localStorage に持つ

**メリット:**

- URL が汚れない。次に開いたときも前回のままになる

**デメリット:**

- 戻るボタンが効かない（履歴と無関係のため）
- 状態を人に渡せない
- 「前回の絞り込みが残っている」状態で開くことになり、書架から本が消えたように見える

## 決定

**案B: URL のクエリを正とし、`history.pushState` / `replaceState` で書く** を採用する。

ただし**並べ替えと表示形式だけは案Cを併用**し、`localStorage` にも覚える。クエリに指定が無いときの既定値として使う。絞り込みの語とタグは覚えない。

## 根拠

### 1. 3つの指摘のうち2つは「置き場」ではなく「履歴の積み方」の問題（Intent 1）

リロードで戻らないのは状態が URL に無いからで、戻るボタンが効かないのは履歴が積まれていないから。前者は案Bで解決するが、後者は**書き方（push か replace か）**で決まる。そこで「利用者が能動的に選んだ変化」は `pushState`、「連続して変わるもの」は `replaceState` と分けた（設計ルール R2）。

### 2. サーバーから取り直さない（Intent 2）

一覧はすでに全件を持っているため、並べ替えもページ送りもクライアント側で完結する。Next の router で遷移するとサーバーコンポーネントが再実行され、DB への問い合わせが毎回走る。`pushState` / `replaceState` は router と同期することが公式ドキュメントに明記されているので、URL だけを書き換えれば足りる。

> "`pushState` and `replaceState` calls integrate into the Next.js Router, allowing you to sync with `usePathname` and `useSearchParams`."
> （`node_modules/next/dist/docs/01-app/01-getting-started/04-linking-and-navigating.md`）

### 3. 覚えるのは「見え方」だけにする（Intent 3）

並べ替えと表示形式は、その人の好みであって対象の限定ではない。一方、絞り込みの語とタグは「いま何を探しているか」であり、次に開いたときも残っていると、書架から本が消えたように見える。そのため**記憶の対象を見え方に限った**。

URL に指定があるときは記憶より URL を優先する。共有された URL の見え方を、受け取った側の記憶で上書きしないため。

## Consequence（結果・トレードオフ）

**得られるもの:**

- リロード・戻る・進む・共有のすべてで同じ画面に戻る
- 並べ替えとページ送りがサーバーへの問い合わせを伴わない
- 編集中のブックマークも URL に載るため、編集画面のまま再読み込みできる

**失うもの / 引き受けるトレードオフ:**

- URL が長くなる（既定値はクエリに出さないことで、素の状態では `/` のままに保つ）
- 操作を足すたびに「履歴を積むかどうか」の判断が要る
- `localStorage` と URL という2つの置き場ができる。どちらが優先かを決めておかないと食い違う（設計ルール R5 で URL 優先と定めた）
- 記憶は端末ごと。別の端末では既定の見え方から始まる

## 決定していないこと

- **絞り込みの語とタグを記憶するか**：いまは記憶しない。「前回の続きから探したい」という要望が出たときに、期限付きで記憶するかを含めて判断する
- **一覧のサーバー側でのページング**：全件をクライアントへ渡す前提を変えていない。件数が増えて初回表示が重くなったときに決める（そのときは URL のクエリをサーバーへ渡す形になる）
- **タグの絞り込みを OR でも行えるようにするか**：現状は AND 固定
- **`sort_order` の編集 UI**：編集画面から数値で入れる形のままで、一覧上での並べ替え操作（ドラッグ等）は作っていない
  - **追記（2026-09-30）**：表示順を**一覧の並べ替えの基準からも一旦外した**（既定を「追加順の降順」に変更）。編集画面の入力は残しているので値は持ち続ける。手で番号を振る運用に戻すか、表示順そのものを畳むかは未決。あわせて、共有済みの `?sort=order` は読めない値として落ち、既定の追加順の降順に読み替わる

## 再検討のトリガー

- ブックマークの件数が増え、全件をクライアントへ渡す初回表示が重くなったとき（サーバー側ページングに移り、クエリの解釈がサーバーへ移る）
- 一覧に**サーバーから取り直す必要のある状態**を足すとき（例：全文検索をサーバー側で行う）。そのときは `history` API ではなく router での遷移に変える
- 絞り込みの条件を記憶してほしいという要望が出たとき（記憶の対象を「見え方」に限る判断を見直す）
- Next.js が `pushState` / `replaceState` と router の同期を変更したとき（根拠 2 の前提が崩れる）
- 利用者が2人以上になったとき（`localStorage` の記憶は端末ごとなので、サーバー側に持つべきかを判断する）

## 設計ルール

- **R1.** 一覧の状態（絞り込みの語・タグ・並べ替え・向き・ページ・表示形式・編集中の id）は URL のクエリを正とする。同じ値を React state に写して持たない
- **R2.** 履歴の積み方は操作で分ける。**利用者が能動的に選んだ変化（タグ・並べ替え・ページ・表示形式・編集を開く）は `pushState`**、**連続して変わるもの（検索語の入力、編集を閉じる、記憶からの復元）は `replaceState`**
- **R3.** 既定値はクエリに出さない。素の状態の URL は `/` のままにする
- **R4.** ページ番号は URL では 1 始まり、内部では 0 始まりで扱う
- **R5.** `localStorage` に覚えるのは並べ替えと表示形式だけ。**URL に指定があるときは URL を優先する**。キーは `tube-bookmark:archive-view`（テーマの `tube-bookmark:theme` と同じ命名にそろえる）
- **R6.** `localStorage` に触れない環境でも一覧は動くこと。読み書きは必ず例外を握りつぶす

## データモデルへの影響

なし。テーブル・カラムの追加も変更も無い。一覧の並べ替えに `videos.created_at` と `videos.sort_order` を使うため、取得する列に加えた（`app/app/page.tsx`）。

**追記（2026-09-30）**：並べ替えに「更新順」を足し、一覧に追加日と更新日を出すようにしたため、`videos.updated_at` も取得する列に加えた。テーブル・カラムの追加も変更も無い点は変わらない。
