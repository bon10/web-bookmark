# Architecture Decision Records (ADR)

設計上の判断と、その判断を**将来見直すための条件**を記録する場所。コードを読めば分かること（どう実装したか）は書かない。書くのは「なぜそう決めたか」「何を決めなかったか」「どうなったら見直すか」。

関連ドキュメント：

- [ユビキタス言語](../ubiquitous-language.md) — 用語の定義。ADR で新しい概念を決めたら辞書にも足す
- [デザイン方針](../design-system.md) — 意匠の判断はこちら

## 採番とファイル名

単一アプリのリポジトリなのでディレクトリは分けない。`decisions/` 内で連番にする。

| ファイル名 | 本文タイトル |
| --- | --- |
| `adr-XXX-<slug>.md` | `ADR-XXX: <判断内容を端的に示すタイトル>` |

## 書くセクション

| セクション | 中身 |
| --- | --- |
| ステータス | 承認済み / 提案中 / 却下 / 廃止 / 置換済み（ADR-YYY による） |
| タグ | 技術領域を表す短い語を2〜5個 |
| コンテキスト | **過去〜現在の事実**。とくに「この ADR を書くに至ったきっかけ」を具体のファイル・コミット・実測値で示す。「こうしたい」は書かない |
| Intent（意図） | **この判断で最も優先したいこと**。複数あるなら優先順位を付ける。抽象語で止めない |
| 選択肢 | 比較した案。採用しなかった案も残す |
| 決定 | 採用した案 |
| 根拠 | なぜその案が Intent に最も合うか。コンテキストの繰り返しにしない |
| Consequence | 得たもの / 引き受けたトレードオフ |
| 決定していないこと | **空にしない。** 書かないと「書いていない＝決まっている」と誤解される |
| 再検討のトリガー | **空にしない。** 後から満たしたか判定できる観察可能な条件で書く |
| 設計ルール | 実装に落とすときの具体ルール。`R1`, `R2`, … と番号を振って他から参照できるようにする |
| 影響を受けるドキュメント | 更新の要否を判断した結果。**影響なしの項目も残す**（参照導線を兼ねる） |

「コンテキストに書くきっかけ（この ADR を書いた出来事）」と「再検討のトリガー（将来見直す条件）」は別物。混同しない。
